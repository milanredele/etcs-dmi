# AI Agent Instructions for ETCS-DMI

This document provides context and guidelines for AI agents (GitHub Copilot and others) working on the **European Train Control System (ETCS) Driver Machine Interface (DMI)** implementation.

## Project Context
- **Domain**: ETCS DMI, ERA_ERTMS_015560 version 4.0.0 (text under `doc/SRS/ERA_ERTMS_015560_v400/sections/`).
- **System specification**: SUBSET-026 v4.0.0, reference [2] of the DMI specification, is under `doc/SRS/SUBSET-026_v400/` (index with DMI entry points in its `README.md`). Use it for what the on-board does (supervision statuses, modes and transitions, procedures). The markdown of both documents is a search aid: when a table, figure or legend matters, check the PDF page.
- **Scope**: the ETCS DMI with the touch screen layout. NTC (chapters 9 and 12) and the soft-key technology are out of scope by decision (PLAN.md status note); do not implement them.
- **Backlog**: PLAN.md §7, from the audit in `doc/AUDIT-2026-09.md`. Cite real clause numbers only; re-read the clause before relying on a finding.
- **Core Technology**: **Ada 2012** (GNAT compiler).
- **Embedded Constraints**: Targeting resource-constrained systems (32-bit ARM/POWER MCUs, ~128kB RAM, ~1MB Flash).
- **No dependencies**: The application uses only standard GNAT libraries; no external graphics or OS libraries are allowed.
- **Architecture**: Framebuffer-based rendering with fonts and symbols pre-rendered as Ada source bitmaps.

## Codebase Structure
The repository holds two products that share a wire protocol: the DMI and the
ETCS on-board (EVC). The on-board is being built in phases, see
[doc/EVC-PLAN.md](doc/EVC-PLAN.md).

- **`dmi/`** — the DMI. `DMI_Core` is the transport independent core
  (Initialise / Handle_Message / Tick / Render / Take_Outbox) and supervises
  the EVC link (silence → mode SF).
    - `Display`: layout and coordinate ranges ([dmi/display.ads](dmi/display.ads)).
    - `Display-X_Area`: sub-packages per screen area (A, B, C, D, …), following ETCS naming.
    - `Display-Frame_Buffer`: pixel drawing ([dmi/display-frame_buffer.ads](dmi/display-frame_buffer.ads)).
- **`evc/`** — the ETCS on-board, SUBSET-026. `EVC_Core` has the same shape as
  `DMI_Core` (Initialise / Handle_Input / Tick / Take_Outputs) behind enumerated
  ports (BTM, RTM, odometer, TIU, DMI, ATO, JRU). Its safety kernel is SPARK
  (`SPARK_Mode`), proven with gnatprove: see the plan for what is in the kernel.
- **`common/`** — shared by both: the DMI–EVC protocol
  ([common/dmi_protocol.ads](common/dmi_protocol.ads)) and `DMI_Link`, the
  reassembly of protocol frames from any byte stream.
- **`sim/`** — the environment simulator for the bench and the regression
  runners: track, train dynamics, automatic driver, the ATO on-board, and
  `EVC_Mock`, the simplified on-board the DMI goldens were recorded
  against (the real on-board of `evc/` replaced it as the bench page's
  default at the end of plan phase E4; the mock stays selectable there).
- **`ports/hosted/`** — the native TCP mains `dmi.adb` and `evc_sim.adb` for the
  hub setup. The wasm glue lives with the bench in `test/wasm/`; a Hercules
  port comes in plan phase E8.
- **Testing & Tooling**:
    - `test/wasm/`: browser test bench. The DMI and the ETCS on-board of `evc/` in the bench environment of `sim/` (`Sim_Onboard_Env`) are built to WebAssembly (`build.sh`, Docker + GNAT-LLVM/AdaWebPack) as `dmi.wasm` and `onboard.wasm`, the default pair since phase E4; `index.html` is the display, touch screen, desk, the on-board's track and train interface panel and a fault-injecting wire. A third module, `evc.wasm`, the simplified on-board `EVC_Mock` the DMI's goldens were recorded against, stays selectable (the "On-board" selector); with it, `smoke.js` cross-checks the wasm rendering against those native goldens. `onboard_smoke.js` checks `onboard.wasm` byte for byte against the native golden `test/golden/evc/bench_onboard.sha256`, that the driver's start of mission on the DMI's own frames reaches SR then FS and stops before the end of authority, and that the page selects the real on-board by default; the page's second track preset (`EVC_Track.Preset_T`, "features demo") exercises On Sight, a level transition and back, override, a Shunting area and a text message the default mission does not.
    - `test/tools/`: a Node.js hub ([server.js](test/tools/server.js)) and HTML client ([client.html](test/tools/client.html)) for the TCP setup; `frame2png.py` renders frame dumps; `efs_frames.py` converts the ERTMSFormalSpecs test frames into `test/efs/` (`--check` verifies); `golden_review.py` turns a changed set of goldens into a reviewable report (`--base`/`--head` revisions or the working tree, `--areas`/`--intent` the declared expectation), pictures included (`golden_review/dmi_areas.adb`, a helper compiled against the area table of the revision under review).
    - `test/src/`: the golden-frame regression runner (`dmi_test`; its scenarios live in `DMI_Test_<Subject>` packages by area/window — `DMI_Test_Supervision`, `_Messages`, `_Planning`, `_Windows`, `_Data_Entry`, `_Settings`, `_VBC`, `_System_Status`, `_ATO`, `_Language`, `_Robustness` — with the shared reset/press/window helpers in `DMI_Test_Support`; a new scenario goes into the matching subject package and is called from `dmi_test.adb` in its place) and the on-board's (`evc_test`; its scenarios live in `EVC_Test_<Subject>` packages by phase — `EVC_Test_Core`, `_Language`, `_Position`, `_Profiles`, `_Supervision`, `_Mission`, `_PBD`, `_Bench`, `_EMRRLS`, `_Config`, `_Modes` — with the check counters, golden/dump comparison, output capture and decoding, simulated track and speed/distance monitoring reference model shared in `EVC_Test_Support`; a new scenario goes into the matching subject package and is called from `evc_test.adb` in its place; phase E4's procedures and touch-only start of mission stay their own generic packages, `EVC_Test_Procedures` and `Evc_Test_Touch`), the fuzzer and host-only helpers (`Display.Screen.Files`) — keep file I/O and GNAT-only packages out of `dmi/`, `evc/`, `common/` and `sim/`, which must build for the wasm32 light runtime and the bare-board runtimes (no tasking, no exception propagation, no `Interfaces.C`, no dynamic allocation). `Scn_Reader` is the generic reader of the line oriented `.scn` scenario format family (opening a file, lines with line numbers, comments and blank lines skipped, words, `Field`, `To_Real`, a `*.scn` directory listing); `evc_efs_test` runs the ERTMSFormalSpecs frames of `test/efs/` against the supervision units on top of it, `evc_s076_check` the SUBSET-076 test sequences of a sibling checkout against the telegram/message codec, and `evc_s076_run` (`S076_Main`, `S076_Run`, `S076_Bench`, `S076_Sequences`, `S076_Tables`) replays those sequences against the whole on-board through its ports, with `DMI_Core` in the loop for the driver's touches, all keeping their own format's keywords and checks to themselves. `Evc_Test_Touch` (generic, instantiated with `Check` like `EVC_Test_Procedures`) drives a native start of mission with `DMI_Core` and `EVC_Core` connected as the bench page connects them, the driver acting only through touch coordinates taken from `DMI_Windows.Button_Area` and `Display.C_Area` — a window-internal button index (Tables 22-25, 29) is derived from the public `DMI_Data_Entry.Max_Fields`, never a copied pixel.
    - `test/efs/`: the functional test frames of ERTMSFormalSpecs (an executable model of SUBSET-026 3.4.0) as scenarios `*.scn`, generated by `test/tools/efs_frames.py` from a checkout next to the repository (`../ERTMSFormalSpecs`, or `--efs`). **Licence rule**: this folder is derived data under the EUPL v1.1 (`test/efs/LICENSE`, provenance in its `README.md`), not under the GPL of the repository; put nothing else there, never edit it by hand, and keep everything outside it independent of it (deleting the folder must leave the build and `test/check.sh` green: the runner and `--check` skip). The converter and its table of known differences (`EXPECTED_DIFFERENCES`, the `xfail` lines) are ours.
    - SUBSET-076 test sequences: generated by a sibling repository, `../etcs-subset076` (or `$S076_CHECKOUT`) next to this one, as `sequences/<SV>/*.scn` in the same scenario format family as `test/efs/`. Like the EFS checkout, it is optional: `obj/evc_s076_check` says so and succeeds when it is absent (`test/s076-sample/` is a small hand-written fixture in that format, kept for development when the sibling has nothing yet; `test/s076-sample/runner/` is the fixture of `evc_s076_run`, one sequence passing, one failing on purpose, one blocked, run always). `test/s076/baseline.csv` is the runner's baseline (name, outcome, step, reason code or failure signature id; no SUBSET-076 text) and `test/s076/triage.csv` the triage of its failure signatures.
- **Utilities (`utils/`)**:
    - C programs for converting `.ttf` and `.bmp` files into Ada source constants.
- **Build projects**: `etcsdmi.gpr` builds everything on the host (Alire crate);
  `etcs_evc.gpr` is the on-board alone for the cross and proof builds;
  `test/wasm/etcsdmi_wasm.gpr` the bench.

## Guidelines for AI Agents

### 1. Ada 2012 Implementation
- **Strong Typing**: Use Ada subtypes and ranges extensively ([dmi/display.ads](dmi/display.ads#L34-L52)) to enforce safety at compile-time and runtime.
- **Naming Convention**: Use `Parent-Child.ads/adb` for packages, translated to `parent-child.ads/adb` file names (e.g., `Display.Area_A` is in [dmi/display-a_area.ads](dmi/display-a_area.ads)).
- **No Dynamic Allocation**: Avoid `new` or `Unbounded_String`. All data structures must be static or stack-allocated.

### 2. Graphics and Rendering
- All coordinates and dimensions are defined in [dmi/display.ads](dmi/display.ads). Refer to this file for any UI-related changes.
- Framebuffer interaction should only happen through `Display.Frame_Buffer`.

### 3. Workflow and Building
- **Build**: Use `alr build` to compile the project (Alire package manager). Alternatively, `gprbuild -P etcsdmi.gpr` can be used. The host build is optimised (`-O2`) and uses every core by default (`-j0` is in the project); `ETCS_BUILD=debug` (or `-XETCS_BUILD=debug`) builds without optimisation into `obj/debug` for a debugger. The on-board alone: `gprbuild -P etcs_evc.gpr`; for the TMS570, `ports/tms570/build.sh` (toolchain via `ports/tms570/setup-toolchain.sh`).
- **Proof**: `evc/prove.sh` (gnatprove on `etcs_evc.gpr`) must report no unproved check. Proof results are shared across worktrees and branches through gnatprove's file cache (`~/.local/share/etcs-dmi/proof-cache`, set in the gpr), so a fresh worktree re-proves only what changed; use `evc/prove.sh -u <unit>` during development, the full run once at the end, and `--replay` to verify a merge. The provers are CVC5 and Z3 with a limit in steps (100000, with 60 s as a backstop), so a result does not depend on the load of the machine; `prove.sh` also fails when a proved check needs more than 60000 steps or 20 s ("too close to the limit": make that proof easier with an assertion, a lemma or a smaller subprogram, do not raise the limit), prints the margin of the run, and lets only one proof run on the machine at a time (a second one waits). It also counts the checks of 16 VCs or more and fails above 6 (`ETCS_PROOF_MAX_WIDE`; today 4, postconditions over many paths): gnatprove unrolls a loop without a loop invariant when it has at most 20 iterations (by its bounds, or by the range of their types: `1 .. X.Count`), and every check of its body splits into one VC per iteration and path. Give such a loop an invariant, the one needed after it or `True` when nothing is; `evc/prove.sh --info` lists the loops gnatprove unrolls. Every message that is not a proved check is shown; the full output is `obj/evc/prove.log`.
- **Generated code**: `evc/language/` holds Ada generated from `etcs_language.toml`; never edit it by hand, run `python3 evc/language/gen_language.py` and keep `--check` green. Every unit under `evc/` is `SPARK_Mode => On`; a unit that cannot be SPARK says why in its header.
- **Robustness**: `obj/dmi_fuzz` and `obj/evc_fuzz` must report `raised: 0`; `obj/evc_fuzz` also fails when its stored information phase loses its coverage (the cycles with an MA below a tenth, a mode it visits without a cycle: see its summary line). Code under `dmi/`, `evc/` and `common/` must never raise on any message, input, touch or tick: validate and ignore, clamp, or draw nothing.
- **Whole check**: `test/check.sh` builds everything and runs the four test programs, the checkers (generator, catalogue, matrix, `golden_review.py --check-tool`), the EFS frames (`efs_frames.py --check`, `obj/evc_efs_test`) and the SUBSET-076 sequences (`obj/evc_s076_check`, `obj/evc_s076_run`); run it before every merge. The checks run side by side and are reported in a fixed order (`CHECK_SERIAL=1` runs them one after the other); a failing check fails the script with its exit status. The proof (`evc/prove.sh`) and the cross build (`ports/tms570/build.sh`) are separate because they take long.
- **Regression**: `obj/dmi_test` and `obj/evc_test` must stay at zero failures; a changed golden is reviewed with `test/tools/golden_review.py` (base and intent given) before `UPDATE=1` re-records: a display group is described from `BLIND.md` by a reviewer who does not know the intent (a small model, Haiku class, is enough), an on-board group gets the tool's own deterministic change summary instead (counting and pairing records is not a describing job); either way `REPORT.md` judges the result against the intent; the verdicts and any side effects go into the commit message.
- **EFS frames**: `obj/evc_efs_test` must report 0 failures. A new failure is analysed (a 3.4.0 vs 4.0 difference citing both clauses, a translation issue, or a defect of ours, which is fixed in `evc/`); a known difference goes into `EXPECTED_DIFFERENCES` of `test/tools/efs_frames.py`, then `python3 test/tools/efs_frames.py` regenerates `test/efs/`.
- **SUBSET-076 sequences**: `obj/evc_s076_check` must report 0 failures against `../etcs-subset076` (or `$S076_CHECKOUT`); a failure is analysed like an EFS one (our defect, a format detail the reader needs to learn, or a field this on-board does not model, left uncompared). What the codec refuses is counted as "rejected", not failed: the sequences carry data meant to be refused, and the runner of E4 judges the reaction. A field width that differs because the on-board operates in an earlier system version (chapter 6) is a rejection too; a genuine defect of SUBSET-076 goes into the `Known` table of the check with its reason. Optional like the EFS checkout: absent, the runner says so and succeeds.
- **SUBSET-076 runner**: `obj/evc_s076_run` replays every sequence against the on-board (EVC_Core through its ports, DMI_Core in the loop, a train model of `S076_Bench`) and gives every step passed, failed or not judged (a fixed list of reasons: level 2/3 or RBC (E5), another system version or Euroloop (E7), E6, NTC, ATO, DMI internal, JRU or input not modelled, extractor, optional step, SUBSET-076 defect, runner gap; never counted as passed), and every sequence passed, failed at step N, or blocked at step N by a reason (the steps after it not run). It writes one summary line, the report `obj/evc_s076_run.txt` (per system version, blocks and not-judged steps by reason, failed sequences by triage, failure signatures ranked, per feature) and compares with `test/s076/baseline.csv`: a sequence that stops earlier than in the baseline, or fails where it was blocked, is a regression and fails the run (`check.sh` too); improvements are reported. `UPDATE=1` re-records the baseline once a change is understood. `VERBOSE=1 obj/evc_s076_run <name or path>` prints the steps of one sequence with the on-board's state (`DEBUG=1` adds the brakes and the JRU records of each step's window), `S076_ONLY=sv30` limits the corpus. A new failure signature is analysed and triaged in `test/s076/triage.csv` (signature id or `~text`, category, note): a defect of ours is fixed in `evc/` with a scenario in `evc_test` citing the clause and the proof (`onboard` while still open); a gap of the runner's model (train, driver, chart speeds) is fixed in `test/src/s076_*` or triaged `model`; a SUBSET-076 or extraction defect is triaged `s076` (or blocked as `S076-defect` in `S076_Run`, like the `Known` table of the check); what a later phase brings is triaged `E5`, `E6` or `E7`. The report must show no signature with `triage: NONE`.
- **Wasm toolchain**: `test/wasm/build.sh` builds natively with the GNAT-LLVM/AdaWebPack toolchain that `test/wasm/setup-native-toolchain.sh` installs outside the repo (`$ETCS_TOOLS/adawebpack-native`), else in the Docker image of `test/wasm/Dockerfile` (kept for CI; `WASM_NATIVE=0|1` forces either).
- **Visual Testing** (browser bench): `test/wasm/build.sh`, then serve the repository over HTTP and open `test/wasm/`; `node test/wasm/smoke.js` verifies the wasm build against `EVC_Mock`, `node test/wasm/onboard_smoke.js` the real on-board.
- **Visual Testing** (TCP setup):
    1. Start the hub: `node test/tools/server.js`
    2. Open `test/tools/client.html` in a browser.
    3. Run the compiled `dmi` and `evc_sim` binaries (or `evc_onboard`, the real on-board, in place of the simulator).

### 4. Safety Considerations
- This project implements a safety-critical interface. When suggesting logic, prioritize clarity, predictability, and conformance to ETCS specifications over "clever" solutions.
